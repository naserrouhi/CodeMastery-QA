# Q8-1: What is REST API?

- REST (REpresentational State Transfer) is an architectural style for building HTTP-based services
- Where you model, resources (things), and operate on them with standard HTTP semantics (like GET).
- REST is not a protocol.

- Core Constraints:

  1. Client–Server: separation of concerns of UI/client and API/server.
  2. Stateless: each request must contain all needed info (no server-side session). Simplifies scaling and caching.
  3. Cacheable: responses should declare if cacheable (Cache-Control).
  4. Uniform Interface: consistent resource identification (URIs), standard methods, representations, and hypermedia (HATEOAS).
  5. Layered System: intermediaries (proxies, gateways, load balancers) can exist without clients knowing.
  6. Code on demand (optional): server can send executable code (rare in APIs).

- HATEOAS and code-on-demand are rarely fully implemented in commercial APIs;
- designers usually focus on stateless, uniform interface, and caching.

- HTTP semantics:

  - GET: read-only, cacheable, should not change server state; idempotent.
  - POST: create-or-do-an-action; not idempotent by default.
  - PUT: replace/update the resource; idempotent.
  - PATCH: partial update.
  - DELETE: remove resource; idempotent.

- Example:

```csharp
[ApiController]
[Route("api/[controller]")]
public class TodosController : ControllerBase
{
    private readonly ITodoRepository _repo;

    public TodosController(ITodoRepository repo) => _repo = repo;

    [HttpGet]
    public async Task<ActionResult<IEnumerable<TodoDto>>> GetAll(int page = 1, int pageSize = 20)
    {
        var items = await _repo.GetPageAsync(page, pageSize);

        return Ok(items);
    }

    [HttpGet("{id}", Name = "GetTodo")]
    public async Task<ActionResult<TodoDto>> Get(int id)
    {
        var item = await _repo.GetAsync(id);
        if (item is null)
          return NotFound();

        return Ok(item);
    }

    [HttpPost]
    public async Task<IActionResult> Create(CreateTodoDto dto)
    {
        var entity = new Todo { Title = dto.Title, Description = dto.Description };
        await _repo.AddAsync(entity);
        var result = new TodoDto(entity);

        return CreatedAtRoute("GetTodo", new { id = entity.Id }, result);
    }

    [HttpPut("{id}")]
    public async Task<IActionResult> Replace(int id, UpdateTodoDto dto)
    {
        if (!await _repo.ExistsAsync(id))
          return NotFound();

        await _repo.UpdateAsync(id, dto);

        return NoContent();
    }

    [HttpDelete("{id}")]
    public async Task<IActionResult> Delete(int id)
    {
        if (!await _repo.ExistsAsync(id))
          return NotFound();
        
        await _repo.DeleteAsync(id);

        return NoContent();
    }
}
```

- Tips:

  - use `[ApiController]` (automatic model validation + 400 on bad model)
  - use DTOs and mapping (avoid leaking DB schema) - breaks versioning;
  - return `CreatedAt` after creation.
  - centralize exceptions via middleware (ProblemDetails).
  - Don’t ignore `Content-Type`/`Accept`. support common formats (JSON) and content negotiation when needed.
  - Avoid GET with request body — some clients/proxies don’t support it.

- Practical best practices:

  - Use nouns (resources) in URIs; do not use verbs (avoid `/api/createUser`).
  - Keep APIs stateless — include auth token in each request.
  - Version your API (e.g., header `Accept: application/vnd.myapi.v1+json` or `api/v1/…`).
  - Use pagination, filtering, and sorting for list endpoints (avoid returning millions).
  - Standardize error responses (RFC7807 ProblemDetails in .NET).
  - Use `ETag` / `If-Match` or optimistic concurrency for concurrent updates.
  - Add OpenAPI/Swagger docs.
  - Secure endpoints (auth, HTTPS, rate limiting), validate input and size, and log correctly.

- Common mistakes:

  - Returning 200 for create —> prefer 201 + Location.
  - Assuming HATEOAS is required — Fielding’s REST includes HATEOAS, but most production APIs skip it;

- Questions:

  1. PUT vs PATCH vs POST?
    - PUT = idempotent replacement, PATCH = partial update, POST = create or perform non-idempotent actions.
  
  2. Do you always follow REST strictly?
    - We follow REST principles pragmatically and choose what best fits product constraints; don’t dogmatically insist on HATEOAS if team doesn’t need it.

  3. GraphQL vs REST?
    - GraphQL helps flexible queries and reduces round-trips but complicates caching, introduces more server-side query control;
    - REST is simpler for standard CRUD and caching.

  4. What if you want all orders for a customer?
    - `GET /customers/45/orders` (nested resource)

- Pros & Cons:

| Pros                         | Cons                               |
| ---------------------------- | ---------------------------------- |
| Simple, uses HTTP directly   | Can over-fetch or under-fetch data |
| Widely supported in tools    | Less flexible in complex queries   |
| Easy to cache (GET requests) | Versioning can be messy            |
