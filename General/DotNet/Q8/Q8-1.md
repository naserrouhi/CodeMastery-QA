# Q8-1: What is REST API?

- REST (Representational State Transfer) is an architecture style for designing networked applications using HTTP.
- You expose resources (data) via URLs, and clients interact with those resources using HTTP methods like GET.
- Architecture for HTTP-based APIs with resource-oriented URLs.
- It is based on resources, which are represented as URLs.
- It’s not a protocol, but a set of constraints that make an API RESTful.
- Statelessness: REST APIs must not store user session/server state.
- REST is not a protocol, it’s an architecture style.

- HTTP Standard Methods and Actions:

| HTTP Verb | What it does            |
| --------- | ----------------------- |
| `GET`     | Read data               |
| `POST`    | Create new data         |
| `PUT`     | Update entire resource  |
| `PATCH`   | Update part of resource |
| `DELETE`  | Delete a resource       |

- Example:

```csharp
[ApiController]
[Route("api/[controller]")]
public class BooksController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll() => Ok(BookStore.GetAll());

    [HttpGet("{id}")]
    public IActionResult Get(int id) => Ok(BookStore.GetById(id));

    [HttpPost]
    public IActionResult Create(Book book)
    {
        var created = BookStore.Add(book);
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created);
    }

    [HttpDelete("{id}")]
    public IActionResult Delete(int id)
    {
        BookStore.Delete(id);
        return NoContent();
    }
}
```

- The Core Principles of REST:

  - Statelessness: No client context is stored on the server.
  - Uniform Interface: Consistent way of interacting with resources.
  - Cacheable: Responses can be cached.
  - Client-server separation
  - Layered system

- Use REST when:

  - You want simplicity. (CRUD style API)
  - You're building a public API.
  - You want easy caching. (e.g., GET)
  - You don’t need nested or flexible queries.

- When REST May Not Be Ideal:

  - If the client needs nested or custom-shaped data.
  - If there's over-fetching (getting too much) or under-fetching (not enough).
  - If you want to combine multiple resources in one call.

- PUT vs. PATCH:

  - PUT: Replaces the entire resource.
  - PATCH: Updates only specified fields.
  - Unlike PUT, PATCH is not guaranteed to be idempotent.

- HATEOAS in REST:

  - Hypermedia As The Engine Of Application State means responses include links to other relevant actions (less common in real apps).

- Pros & Cons:

| Pros                         | Cons                               |
| ---------------------------- | ---------------------------------- |
| Simple, uses HTTP directly   | Can over-fetch or under-fetch data |
| Widely supported in tools    | Less flexible in complex queries   |
| Easy to cache (GET requests) | Versioning can be messy            |

- What if you want all orders for a customer?
  - `GET /customers/45/orders` (nested resource)
