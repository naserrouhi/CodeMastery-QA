# Q8-3: What is OData?

- OData (Open Data Protocol) is a REST-based protocol developed by Microsoft
- To query and manipulate data using standard HTTP + a uniform query syntax (think SQL over HTTP).
- It extends REST by adding query options (like `$filter`) so clients can dynamically shape responses without adding new endpoints.

- It’s standardized:
    - Format: JSON or XML (JSON in modern APIs)
    - Spec: OASIS & ISO/IEC standard

- Example:

    - Plain REST:
        - `/api/products?category=Electronics&sort=price&minPrice=100&fields=name,price&limit=5`

    - OData:
        - `/api/products?$filter=category eq 'Electronics' and price gt 100&$select=name,price&$orderby=price&$top=5`

- OData Query Options:

| Example                                              |
| ---------------------------------------------------- |
| `$filter=price gt 100 and category eq 'Electronics'` |
| `$select=name,price`                                 |
| `$orderby=price desc`                                |
| `$top=10`                                            |
| `$skip=20`                                           |
| `$expand=Category`                                   |
| `$count=true`                                        |

- OData in .NET:

Using **Microsoft.AspNetCore.OData**:

```csharp
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    public string Category { get; set; } = "";
}

[Route("api/[controller]")]
public class ProductsController : ODataController
{
    private static readonly List<Product> Products = new()
    {
        new Product { Id=1, Name="Laptop", Price=1200, Category="Electronics" },
        new Product { Id=2, Name="Shoes", Price=80, Category="Fashion" }
    };

    [EnableQuery]
    public IActionResult Get()
    {
        return Ok(Products.AsQueryable());
    }
}

builder.Services.AddControllers().AddOData(opt => opt.Select().Filter().OrderBy().Count().Expand().SetMaxTop(100));

app.MapControllers();
```

- Pros:

    - Very powerful querying without extra endpoints.
    - Standard syntax → same rules for all entities.
    - Built-in in .NET → minimal setup.
    - Can save development time for internal/business apps.

- Cons:

    - Overkill for simple APIs.
    - If exposed publicly → risk of over-querying DB (performance hit).
    - Query syntax can be too powerful for security (e.g., exposing internal fields).
    - Caching harder (queries are dynamic).

- When to Use?

    - Internal business apps where users need flexible data queries.
    - Rapid prototyping of data-driven APIs.
    - APIs consumed by multiple different clients with varying data needs.

- Avoid if:

    - Public API with heavy traffic (could be abused).
    - Data security rules are strict (OData can expose fields unintentionally).

- Common Mistakes:

    - Not limiting \$top — clients can request millions of rows.
    - Allowing unrestricted \$expand — can cause massive joins.
    - Exposing internal fields accidentally (always control what’s exposed in `[EnableQuery]`).
    - Assuming OData replaces REST --> it’s still REST, just with query conventions.

- How does OData compare to GraphQL?

    - Both let clients shape responses dynamically.
    - But OData uses standard query syntax over REST;
    - GraphQL has a strongly typed schema and single endpoint.
    - OData is simpler for CRUD over relational data.

| Feature           | REST             | GraphQL             | OData                                     |
| ----------------- | ---------------- | ------------------- | ----------------------------------------- |
| Query flexibility | Low              | High                | Medium-High                               |
| Standardization   | Low              | High (schema)       | High (query syntax)                       |
| Caching ease      | High             | Hard                | Medium                                    |
| Learning curve    | Low              | Medium-High         | Medium                                    |
| Best for          | Simple CRUD APIs | Complex/nested data | Data-heavy APIs needing filtering/sorting |
