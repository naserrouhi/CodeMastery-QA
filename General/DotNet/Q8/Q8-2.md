# Q8-2: What is GraphQL?

- It is a query language for APIs and a runtime for executing those queries against your data.
- It was developed by Facebook.
- Instead of multiple REST endpoints, you send a single query describing the exact shape of data you want.

| Building Block | Purpose                                                         | Example                                               |
| -------------- | --------------------------------------------------------------- | ----------------------------------------------------- |
| Schema         | Contract between client & server; defines types and operations. | `type User { id: ID!, name: String!, posts: [Post] }` |
| Queries        | Read operations.                                                | `{ user(id:1) { name, posts { title } } }`            |
| Mutations      | Write operations (create/update/delete).                        | `mutation { createUser(name:"Naser") { id, name } }`  |
| Subscriptions  | Real-time updates over WebSocket.                               | `subscription { messageAdded { id, text } }`          |

- Example:

```graphql
{
  user(id: 1) {
    name
    posts {
      title
      commentsCount
    }
  }
}
```

```json
{
  "data": {
    "user": {
      "name": "Naser",
      "posts": [
        { "title": "REST vs GraphQL", "commentsCount": 12 },
        { "title": "gRPC Basics", "commentsCount": 5 }
      ]
    }
  }
}
```

- GraphQL in .NET:

```bash
dotnet add package HotChocolate.AspNetCore
```

```csharp
public record User(int Id, string Name);
public record Post(int Id, string Title, int UserId, int CommentsCount);

public class Query
{
    public User GetUser(int id) => new(id, "Naser");

    public IEnumerable<Post> GetPosts(int userId) =>
        new List<Post> {
            new Post(1, "REST vs GraphQL", userId, 12),
            new Post(2, "gRPC Basics", userId, 5)
        };
}

builder.Services
       .AddGraphQLServer()
       .AddQueryType<Query>();

app.MapGraphQL();
```

- Run & test:
  - Open `/graphql` → use **Banana Cake Pop** playground to run queries.

- Pros & Cons:

| Pros                                  | Cons                                                |
| ------------------------------------- | --------------------------------------------------- |
| less over-fetching                    | More complex server setup                           |
| Single request for nested data        | Caching harder than REST (no built-in HTTP caching) |
| Strongly typed schema & introspection | Potential for expensive queries                     |
| Self-documenting (via schema)         | Needs query complexity control for performance      |
| Real-time subscriptions possible      | Learning curve for both backend & frontend          |

- When to Use?

  - Complex UIs needing multiple related resources in one request.
  - Mobile apps where bandwidth is precious.
  - Public APIs where flexibility is key.
  - Systems with rapidly evolving data needs.

- Avoid if:

  - Simple CRUD with predictable endpoints (REST is simpler and easier to cache).
  - Data mostly comes from one table/entity (overkill).

- Common Mistakes:

  - Allowing unbounded queries --> fix with query depth limits & cost analysis.
  - Ignoring N+1 problem --> use batching (`DataLoader`).
  - Over-engineering small projects.
  - Not versioning --> GraphQL is “evolvable”, but breaking changes still happen; deprecate fields properly.

- Questions:

  1. What’s the N+1 problem in GraphQL?
    - When resolving nested fields, resolvers can trigger multiple DB queries per item, causing performance issues. Fixed with batching/caching.

  2. How do you secure a GraphQL API?
    - Auth at resolver level, query depth/complexity limits, rate limiting, avoid exposing sensitive schema fields.

| Feature            | REST                           | GraphQL                       |
| ------------------ | ------------------------------ | ----------------------------- |
| Data Fetching      | Fixed endpoints, full resource | Flexible query, exact fields  |
| Multiple Resources | Multiple requests              | One request                   |
| Caching            | Easy with HTTP                 | Harder, custom logic          |
| Schema             | Implicit                       | Explicit & typed              |
| Versioning         | Via URL or headers             | Schema evolution, deprecation |
