# Q8-4: What is gRPC?

- gRPC (Google Remote Procedure Call) is a high-performance, open-source RPC framework.

- It uses:

    - HTTP/2 as the transport (multiplexing, compression, streaming)
    - Protocol Buffers (Protobuf) for serialization (binary, compact, strongly typed)
    - Contract-first development (you define a `.proto` file, generate code for client/server)

- Think of it as:
    - Instead of sending JSON over HTTP like REST, gRPC sends binary messages defined by a schema, over a fast HTTP/2 connection.

- It solves limitations of REST in low-latency, high-throughput, microservice-to-microservice communication:

    - REST/JSON is text-based (verbose) → gRPC/Protobuf is binary (smaller, faster to parse)
    - HTTP/1.x makes multiple requests sequential → HTTP/2 multiplexes streams
    - REST endpoints are resource-oriented → gRPC is function/method-oriented

- Communication Types:

    1. Unary → client sends one request, gets one response (like a normal function call).
    2. Server streaming → client sends one request, server streams back multiple responses.
    3. Client streaming → client streams multiple requests, server responds once.
    4. Bidirectional streaming → both sides send messages in parallel.

- Example:

- `.proto` file (contract)

```proto
syntax = "proto3";

option csharp_namespace = "ProductGrpcService";

service ProductService {
  rpc GetProduct (ProductRequest) returns (ProductResponse);
  rpc ListProducts (ListProductsRequest) returns (stream ProductResponse);
}

message ProductRequest {
  int32 id = 1;
}

message ListProductsRequest {
  string category = 1;
}

message ProductResponse {
  int32 id = 1;
  string name = 2;
  double price = 3;
}
```

- Server in .NET

```csharp
public class ProductServiceImpl : ProductService.ProductServiceBase
{
    public override Task<ProductResponse> GetProduct(ProductRequest request, ServerCallContext context)
    {
        return Task.FromResult(new ProductResponse
        {
            Id = request.Id,
            Name = "Laptop",
            Price = 1200
        });
    }

    public override async Task ListProducts(ListProductsRequest request,
                                            IServerStreamWriter<ProductResponse> responseStream,
                                            ServerCallContext context)
    {
        var products = new[]
        {
            new ProductResponse { Id = 1, Name = "Laptop", Price = 1200 },
            new ProductResponse { Id = 2, Name = "Mouse", Price = 25 }
        };

        foreach (var product in products)
        {
            await responseStream.WriteAsync(product);
            await Task.Delay(500); // simulate delay
        }
    }
}
```

- Client in .NET

```csharp
var channel = GrpcChannel.ForAddress("https://localhost:5001");
var client = new ProductService.ProductServiceClient(channel);

// Unary
var product = await client.GetProductAsync(new ProductRequest { Id = 1 });
Console.WriteLine(product.Name);

// Server streaming
using var call = client.ListProducts(new ListProductsRequest { Category = "Electronics" });
await foreach (var p in call.ResponseStream.ReadAllAsync())
{
    Console.WriteLine(p.Name);
}
```

- Pros:

    - Super-fast (binary + HTTP/2)
    - Contract-first → no client/server mismatch
    - Streaming support out of the box
    - Language-agnostic (generate clients in Java, Go, Python, etc.)
    - Great for microservices

- Cons:

    - Not human-readable (binary messages)
    - Harder to debug without tooling
    - Limited browser support (needs gRPC-Web for frontend)
    - Overkill for public APIs where JSON/REST is fine

- When to Use?

    - Microservices communication inside a data center
    - Real-time streaming (chat, telemetry, IoT)
    - Cross-language internal APIs
    - Low latency & high performance critical

- Avoid if:

    - Public-facing API for general consumers (JSON is easier to debug)
    - You need simple CRUD with broad client compatibility

- Common Mistakes:

    - Forgetting streaming — many people only use unary RPC; streaming is a big advantage
    - Not versioning proto contracts — breaking changes can crash clients; use field numbers carefully
    - Exposing gRPC directly to browsers — needs gRPC-Web or a gateway like Envoy
    - Assuming it's faster in all cases — for very small payloads, the performance difference may be negligible compared to network latency

- Questions:

    1. How is gRPC different from REST?
        - gRPC is binary, uses HTTP/2, is contract-first, supports streaming, and is method-oriented; REST is text-based, HTTP/1.x-friendly, resource-oriented.

    2. Can browsers call gRPC directly?
        - Not standard gRPC — needs gRPC-Web with a proxy or gateway.

    3. How do you version a gRPC API?
        - Add new fields with new numbers, mark old fields as deprecated; never reuse field numbers.

    4. When would you choose gRPC over GraphQL?
        - For internal service-to-service calls where performance and type safety matter more than flexible querying.

| Feature           | REST             | GraphQL           | OData                   | gRPC                    |
| ----------------- | ---------------- | ----------------- | ----------------------- | ----------------------- |
| Transport         | HTTP 1.x         | HTTP 1.x          | HTTP 1.x                | HTTP/2                  |
| Format            | JSON/XML         | JSON              | JSON/XML                | Binary (Protobuf)       |
| Schema            | Optional         | Strongly typed    | EDM (Entity Data Model) | Strongly typed          |
| Query Flexibility | Low              | High              | Medium-High             | Low (fixed methods)     |
| Streaming         | No               | Subscription (WS) | No                      | Yes                     |
| Best For          | Simple CRUD APIs | Flexible queries  | Data-heavy queries      | High-perf internal APIs |
