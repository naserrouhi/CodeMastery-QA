# Q2-81: What is the difference between classic, quorum, stream queues?

1. Classic Queues

   1. They can operate as standalone queues or be mirrored.
   2. Queue can be durable or not.
   3. Messages can be stored persistent or not.
   4. High throughoutput (Best for small, fast messages)
   5. Eventual consistency (in mirrored queues, some nodes may lag)
   6. Moderate Data Safety (Mirroring may lose messages in split-brain scenarios)
   7. Mirrored classic queues can suffer from performance issues under high load.
   8. Used for simple message queuing where messages must be delivered at least once.
   9. Example: Order Processing System → Each order is placed in a queue and processed by a worker.

```csharp
var factory = new ConnectionFactory() { HostName = "localhost" };
using var connection = factory.CreateConnection();
using var channel = connection.CreateModel();

channel.QueueDeclare(queue: "order_queue",
                     durable: true,
                     exclusive: false,
                     autoDelete: false,
                     arguments: null);

var message = "Order ID: 12345";
var body = Encoding.UTF8.GetBytes(message);
channel.BasicPublish(exchange: "",
                     routingKey: "order_queue",
                     basicProperties: null,
                     body: body);
```

2. Quorum Queues

   1. They cannot be standalone.
        
      - To use them, you need a cluster with at least three nodes.
      - This is because:
         - A majority of nodes must agree on the state of the queue.
         - With three nodes, the system can tolerate the failure of one node and still maintain a quorum.

   2. Queue is durable. (Will face n error if be non durable.)
   3. Messages should store persistance. (Can store non persitance)
   4. Low throughoutput (Rtat replication overhead)
   5. Strong consistency (Raft ensures all nodes agree)
   6. High Data Safety (Raft ensures no data loss, even in leader failure)
   7. Designed to handle high loads more efficiently than classic mirrored queues.
   8. If a node fails, a new leader is automatically elected.
   9. Higher resource usage (disk and memory) due to replication and persistence.
   10. Used for critical financial transactions, banking, or payment processing where message loss is not acceptable.
   11. Example: Banking Transaction Queue

```csharp
channel.QueueDeclare(queue: "transaction_queue",
                     durable: true,
                     exclusive: false,
                     autoDelete: false,
                     arguments: new Dictionary<string, object>
                     {
                         { "x-queue-type", "quorum" }
                     });

var message = "Transaction ID: 98765";
channel.BasicPublish(exchange: "",
                     routingKey: "transaction_queue",
                     basicProperties: null,
                     body: Encoding.UTF8.GetBytes(message));
```

3. Stream Queues

   1. They cannot be standalone.
   2. Queue is durable. (Will face n error if be non durable.)
   3. Messages should store persistance. (Can store non persitance)
   4. Very high throughoutput (Optimized for sequentia reads)
   5. Strong consistency (log-based storage ensures ordered delivery)
   6. High Data Safety (Persistent mesages stored efficiently)
   7. Higher disk usage due to append-only log storage.
   8. Used for real-time analytics, logs, telemetry, and event streaming.
   9. Example: User Activity Logging System

```csharp
channel.QueueDeclare(queue: "activity_stream",
                     durable: true,
                     exclusive: false,
                     autoDelete: false,
                     arguments: new Dictionary<string, object>
                     {
                         { "x-queue-type", "stream" }
                     });

var message = "User clicked button at " + DateTime.UtcNow;
channel.BasicPublish(exchange: "",
                     routingKey: "activity_stream",
                     basicProperties: null,
                     body: Encoding.UTF8.GetBytes(message));
```
