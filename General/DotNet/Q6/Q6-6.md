# Q6-6: What is CQRS?

- CQRS (Command Query Responsibility Segregation) splits your system into two separate paths:
    - Commands: write operations (create, update, delete)
    - Queries: read operations (fetch data)

- Instead of one model doing both, CQRS separates them — improving performance, scalability, and maintainability.

- Key Idea

| Aspect           | Command                     | Query                            |
| ---------------- | --------------------------- | -------------------------------- |
| Purpose          | Change state                | Read data                        |
| Returns          | Nothing or success result   | Data                             |
| Can mutate data? | Yes                         | No                               |
| Handler          | `ICommandHandler<TCommand>` | `IQueryHandler<TQuery, TResult>` |

- Example

```csharp
public class ActivateUserCommand
{
    public int UserId { get; set; }
}

public class ActivateUserCommandHandler
{
    private readonly IUserRepository _repo;

    public ActivateUserCommandHandler(IUserRepository repo) => _repo = repo;

    public void Handle(ActivateUserCommand command)
    {
        var user = _repo.GetById(command.UserId);
        user.Activate();
        _repo.Save(user);
    }
}

public class GetUserByIdQuery
{
    public int UserId { get; set; }
}

public class GetUserByIdQueryHandler
{
    private readonly IUserReadRepository _readRepo;

    public GetUserByIdQueryHandler(IUserReadRepository readRepo) => _readRepo = readRepo;

    public UserDto Handle(GetUserByIdQuery query)
    {
        var user = _readRepo.Find(query.UserId);
        return new UserDto(user.Id, user.Email, user.IsActive);
    }
}
```

- Benefits:

| Benefit                | Why it helps                                                               |
| ---------------------- | -------------------------------------------------------------------------- |
| Separation of concerns | Business rules (commands) vs fast reads (queries)                          |
| Performance            | Queries can be optimized separately (e.g., projections, Dapper, NoSQL)     |
| Scalability            | You can scale read and write sides independently                           |
| Flexibility            | Enables event sourcing, message queues, async processing later             |

- Where to Use CQRS?

| Use it when:                                   | Don’t use when:                   |
| ---------------------------------------------- | --------------------------------- |
| Your system is write-heavy and read-heavy      | App is small or CRUD-based        |
| You need different models for read and write   | One model is enough               |
| You’re building event-driven or microservices  | It adds complexity otherwise      |
| You need scalable reads (caching, projections) | You don’t expect traffic problems |

- Questions:

| Question                                      | Good Answer                                                                   |
| --------------------------------------------- | ----------------------------------------------------------------------------- |
| What is CQRS?                                 | A pattern that splits command and query responsibilities into separate models |
| Why use it?                                   | Improves scalability, separation of concerns, and performance                 |
| Can CQRS be used with Clean Architecture?     | Yes! Use cases become command/query handlers                                  |
| Can you implement CQRS without a message bus? | Yes. CQRS ≠ event sourcing. It can be in-process                              |
| What’s the downside?                          | More code, more layers — overkill for small apps                              |

- Common Pitfalls

| Mistake                                    | Fix                                                   |
| ------------------------------------------ | ----------------------------------------------------- |
| Using same models for command and query    | Separate them!                                        |
| Putting business logic in query            | Queries should be read-only                           |
| Overengineering with MediatR in a TODO app | Use CQRS when complexity requires it                  |
| Confusing CQRS with Event Sourcing         | They are often used together but are not the same     |

- CQRS is often used in large-scale systems.
- But when your system grows into independent components/services, you'll want Microservices Architecture
