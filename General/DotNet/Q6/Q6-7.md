# Q6-7: What is Microservices?

- Microservices architecture structures your application as a collection of small, independent services.

- Each service:

    - Handles one business capability (e.g., Orders, Users)
    - Has its own database
    - Can be deployed and scaled independently

- Key Characteristics

| Feature                | Description                                      |
| ---------------------- | ------------------------------------------------ |
| Independent Deployment | Each service can be updated separately           |
| Loose Coupling         | Services interact via APIs or messaging          |
| Bounded Contexts       | Each service owns a well-defined business area   |
| Own Database           | No shared DB — each service manages its own data |
| Technology Agnostic    | Services can use different languages, frameworks |

- Example System: E-Commerce

| Service              | Responsibility                |
| -------------------- | ----------------------------- |
| User Service         | Login, Register, User profile |
| Product Service      | Catalog, Inventory            |
| Order Service        | Place orders, track status    |
| Payment Service      | Process payments              |
| Notification Service | Send emails, SMS              |

- Each service might expose:

    - REST API (`/api/users`)
    - gRPC endpoint
    - Async queue (`orders.created`)

- Tech Used in .NET Microservices

| Concern               | Technology                              |
| --------------------- | --------------------------------------- |
| API Gateway           | YARP, Ocelot                            |
| Service Communication | REST, gRPC, or RabbitMQ/Kafka           |
| DB per service        | EF Core, Dapper, MongoDB, etc.          |
| Authentication        | IdentityServer, JWT, OAuth2             |
| Deployment            | Docker, Kubernetes                      |
| Observability         | Serilog, Seq, OpenTelemetry, Prometheus |

- Benefits

| Benefit            | Explanation                       |
| ------------------ | --------------------------------- |
| Scalability        | Scale services independently      |
| Flexibility        | Choose best tech per service      |
| Resilience         | Faults are isolated to a service  |
| Faster deployments | Small teams deploy their services |
| Clear boundaries   | Easier to understand, maintain    |

- Challenges

| Challenge        | Description                                              |
| ---------------- | -------------------------------------------------------- |
| Complexity       | DevOps, monitoring, service discovery                    |
| Data consistency | No cross-service transactions (use eventual consistency) |
| Testing          | Integration testing is harder                            |
| Latency          | Network calls instead of method calls                    |

- Questions

| Question                                                  | Tip Answer                                                                   |
| --------------------------------------------------------- | ---------------------------------------------------------------------------- |
| What is a microservice?                                   | A small, independently deployable service focused on one business capability |
| Why use it?                                               | Improves scalability, team autonomy, and resilience                          |
| How do services communicate?                              | REST, gRPC, or asynchronous messaging like RabbitMQ                          |
| How do you handle data sharing?                           | Services own their data; use APIs or events to sync                          |
| What’s the difference between microservices and monolith? | Monolith = single unit, Microservices = distributed components               |
| What about distributed transactions?                      | Use eventual consistency and patterns like Saga                              |

- Common Pitfalls

| Mistake                             | Fix                                                 |
| ----------------------------------- | --------------------------------------------------- |
| Starting microservices too early    | Begin with a modular monolith and split when needed |
| Sharing a database between services | Breaks the autonomy principle                       |
| Not having observability            | Add logging, tracing, monitoring from day one       |
| Poor service boundaries             | Use DDD’s bounded context to define services        |
| Tight coupling via direct calls     | Prefer async events or API gateways                 |

- When to Use Microservices

| Use it when...           | Don't use it when...                               |
| ------------------------ | -------------------------------------------------- |
| You have multiple teams  | You're solo or early-stage                         |
| Scalability matters      | App is simple and doesn't need independent scaling |
| Your domain is complex   | You only have CRUD screens                         |
| You can invest in DevOps | You want fast, simple deployments                  |

- Start with a modular monolith using Clean Architecture or CQRS.
- Split it into microservices when:
    - Teams get large
    - Domain boundaries are clear
    - Scaling and deployments need independence
