# Q6-9: What is DDD?

- Domain-Driven Design (DDD) is a software design approach that focuses on modeling software based on the real business domain.
- The idea: Let the domain (the business rules) drive the design of your system, not the database or the framework.

- Key Principles

| Concept              | Meaning                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| Ubiquitous Language  | Everyone (devs, business) speaks the same language — e.g., "Order", "Approve", "Invoice"         |
| Bounded Context      | Clear boundaries where terms and rules apply. Each domain has its own logic, model, and language |
| Entities             | Domain objects with identity (`User`, `Order`, etc.)                                             |
| Value Objects        | Objects with no identity, compared by value (`Money`, `Email`)                                   |
| Aggregates           | A root entity and its tightly-related children (e.g., `Order` → `OrderItems`)                    |
| Domain Services      | Business logic that doesn't naturally belong to any one entity                                   |
| Application Services | Coordinates use cases (e.g., `CreateOrder`, `ApproveInvoice`)                                    |
| Repositories         | Interfaces for data persistence (e.g., `IOrderRepository`)                                       |
| Factories            | Used to create complex aggregates                                                                |
| Domain Events        | Messages raised from domain actions (e.g., `OrderApproved`)                                      |

- Folder Structure for Clean + DDD

MyApp/
├── Domain/
│   ├── Entities/
│   ├── ValueObjects/
│   ├── Aggregates/
│   ├── Interfaces/              ← Repositories, domain services
│   └── Events/
├── Application/
│   ├── UseCases/                ← Application services or CQRS handlers
│   └── Contracts/DTOs/
├── Infrastructure/
│   └── Persistence/             ← EF Repositories, DbContext
├── Web/                         ← ASP.NET Core
│   └── Controllers/

- Example:

- Entity

```csharp
public class Order
{
    public Guid Id { get; private set; }
    public List<OrderItem> Items { get; private set; }
    public bool IsConfirmed { get; private set; }

    public Order() => Items = new List<OrderItem>();

    public void AddItem(string product, int qty)
    {
        if (IsConfirmed) throw new InvalidOperationException("Order is already confirmed.");
        Items.Add(new OrderItem(product, qty));
    }

    public void Confirm()
    {
        if (!Items.Any()) throw new Exception("Cannot confirm empty order");
        IsConfirmed = true;
        DomainEvents.Raise(new OrderConfirmed(Id));
    }
}
```

- Value Object

```csharp
public class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentException("Amount must be positive");
        Amount = amount;
        Currency = currency;
    }

    public override bool Equals(object obj) =>
        obj is Money m && Amount == m.Amount && Currency == m.Currency;

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);
}
```

- Application Service

```csharp
public class ConfirmOrderUseCase
{
    private readonly IOrderRepository _repo;

    public ConfirmOrderUseCase(IOrderRepository repo) => _repo = repo;

    public void Execute(Guid orderId)
    {
        var order = _repo.Get(orderId);
        order.Confirm();
        _repo.Save(order);
    }
}
```

- Benefits:

| Benefit              | Description                                           |
| -------------------- | ----------------------------------------------------- |
| Business alignment   | Code models the domain, not the database              |
| Complexity isolation | Hard logic lives in the domain, not scattered         |
| Testability          | You can test domain rules without infrastructure      |
| Clear boundaries     | Teams work on bounded contexts independently          |
| Scalability          | You can evolve or split services as your domain grows |

- Common Pitfalls

| Mistake                      | Fix                                                         |
| ---------------------------- | ----------------------------------------------------------- |
| Using DDD for CRUD apps      | Only apply DDD where there is real domain complexity        |
| Over-engineering small apps  | Start simple and grow into DDD when complexity justifies it |
| Skipping Ubiquitous Language | Always align with business terminology                      |
| Thin domain models (anemic)  | Domain entities should have behavior, not just data         |

- When to Use DDD?

    - Business logic is complex or evolving
    - Rules can't be easily expressed via database constraints
    - You want deep alignment between dev team and domain experts
    - You're building long-term, large-scale applications

- Questions

| Question                                               | Good Answer                                                          |
| ------------------------------------------------------ | -------------------------------------------------------------------- |
| What is DDD?                                           | A design approach that models the software after the business domain |
| What's the difference between Entity and Value Object? | Entities have identity; Value Objects are compared by value          |
| What is a Bounded Context?                             | A logical boundary in which a particular domain model applies        |
| What are Aggregates?                                   | A cluster of domain objects with a root (the Aggregate Root)         |
| Where do you place business logic in DDD?              | In Entities or Domain Services — not in controllers or EF models     |
| What are Domain Events?                                | Notifications raised from the domain when important things happen    |
| Why do you use Factories?                              | To encapsulate complex object creation logic                         |
| What is an anemic domain model?                        | A model with no behavior — just getters/setters (anti-pattern)       |
