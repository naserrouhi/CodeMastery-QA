# Q6-3: What is the Onion Architecture?

- It focuses on the core domain and puts infrastructure and external concerns (like database, UI) around it like onion layers.

- It enforces Dependency Inversion Principle.
  - Inner layers should not depend on outer layers.
  - Only outer layers can depend on inner layers.

- Structure (from inner to outer):

[Domain Layer]         ← Core models, logic, interfaces (NO EF, NO DB)
   ↑
[Application Layer]    ← Use cases, services, business rules
   ↑
[Infrastructure Layer] ← DB, external APIs, EF, File I/O (depends on Domain via interfaces)
   ↑
[Presentation Layer]   ← MVC/API/Console UI (depends on Application)

- Folder Structure:

MyApp/
├── MyApp.Domain           // Entities, Value Objects, Interfaces
├── MyApp.Application      // Services, DTOs, UseCases
├── MyApp.Infrastructure   // EF, Repositories, Email, etc.
├── MyApp.Web              // ASP.NET Core API or MVC

- Example

- Domain Layer

```csharp
// Entity
public class User
{
    public int Id { get; set; }
    public string Email { get; set; }
    public bool IsActive { get; private set; }

    public void Activate() => IsActive = true;
}

// Repository Interface
public interface IUserRepository
{
    User GetById(int id);
    void Save(User user);
}
```

- Application Layer

```csharp
public class UserService
{
    private readonly IUserRepository _repo;

    public UserService(IUserRepository repo)
    {
        _repo = repo;
    }

    public void ActivateUser(int id)
    {
        var user = _repo.GetById(id);
        user.Activate();
        _repo.Save(user);
    }
}
```

- Infrastructure Layer

```csharp
public class EfUserRepository : IUserRepository
{
    private readonly AppDbContext _db;

    public EfUserRepository(AppDbContext db) => _db = db;

    public User GetById(int id) => _db.Users.Find(id);
    public void Save(User user) => _db.SaveChanges();
}
```

- Key Principles

  - Core has no dependencies (no EF, no services)
  - Application uses interfaces only
  - Infrastructure implements interfaces
  - Presentation calls application services

- Questions

| Question                                     | Answer / Tip                                                                        |
| -------------------------------------------- | ----------------------------------------------------------------------------------- |
| Why use Onion over N-Layer?                  | Onion protects domain from infrastructure. In N-Layer, domain often depends on DAL. |
| How does Onion enforce dependency direction? | Interfaces go inward; implementations go outward.                                   |
| How do you test the domain?                  | Pure unit tests. No mocking needed. Just test behavior.                             |

- Pitfalls

| Mistake                                      | Fix                                                   |
| -------------------------------------------- | ----------------------------------------------------- |
| No separation between domain and application | Keep domain logic pure, move coordination to services |
| Mixing responsibilities in application       | Each service = one use case or business rule          |

- When to Use Onion?

  - When your app has rich business logic
  - When you care about testability and separation
  - Mid to large apps (onion is scalable)
  - You want to follow DDD

- Onion is domain-centered but still uses layered communication.
- If you want even more flexibility in how components talk (via ports and adapters) and support plugins, it's time for Hexagonal Architecture.
