# Q7-14: What happens when I write async?

1. You Write an `async` Method

    - You’re saying: "I want to write non-blocking code that looks like normal sequential code.".

2. The Compiler Rewrites It into a State Machine

   - Saves the current state. (like a bookmark)
   - Suspends when it hits `await`.
   - Resumes when the awaited task completes.
   - This is called the async state machine.

3. What Happens at `await`?

   - The method exits and returns a `Task` to the caller. (like a promise: "I'll come back later")
   - The `Task` you're waiting on, runs independently.
   - When the `Task` is done, the state machine resumes from where it left off.
   - This is called continuation — it’s scheduled using `SynchronizationContext` or `TaskScheduler`.

4. What Happens to Threads?

   - No new thread is created at `await`.
   - If the `await` is waiting for an I/O (like API call, DB, disk), no thread is used.
   - The OS (or I/O subsystem) waits and notifies .NET when the result is ready.
   - This is asynchronous I/O, not multithreading.

5. What About the Thread Pool?

   - If the awaited method uses `Task.Run(...)`, it uses a thread from the thread pool.
   - But most I/O operations (like `HttpClient.SendAsync`) do not consume threads while waiting.
   - That's why async code scales better — because threads are not blocked.

6. What Does the CPU Do?

   - If your async code is waiting on something (like disk/network), the CPU is free.
   - It can work on other tasks — improving performance.

   - CPU is only used during:
     - initial call setup
     - actual computation (e.g., JSON parsing)
     - resuming after `await`

   - So async code helps the CPU by letting it avoid idle wait time.

7. What Are Virtual Threads?

   - .NET doesn't have Java-style virtual threads, but the idea is similar:

        - Each `async` method acts like a lightweight logical thread.
        - The runtime schedules and switches them efficiently without real OS threads.
        - You can run thousands of async tasks with just a few real threads.

## 🔷 Summary: What Happens When You Write `async`?

| Aspect                     | What Happens                                     |
| -------------------------- | ------------------------------------------------ |
| You call an `async` method | Compiler creates a **state machine**             |
| At `await`                 | Method **pauses**, and control returns to caller |
| While awaiting             | **No thread** is used if it's I/O-based          |
| When task completes        | **Continuation** is posted to resume the method  |
| Thread pool                | Used only if you run CPU work (e.g., `Task.Run`) |
| CPU                        | Stays **available** during I/O waits             |
| Threads                    | Async doesn’t use **new threads** unless needed  |

## 🖼️ Part 1: **Visual Diagram of `async`/`await` Execution Flow**

```text
🔹 Your Code:                        🔹 What .NET Does:

  var result = await SomeAsync();   →   [1] Start method → create Task
                                       [2] Hit `await`: suspend method
                                       [3] Return control to caller

  // Suspended... waits for Task
                                       [4] Task completes (e.g. HTTP done)
                                       [5] Queue continuation to resume
                                       [6] Resume method from await point
                                       [7] Execute remaining code

```

🧠 **Key Point:** The method is not running the whole time — it's paused in memory and **resumed later**, like a “bookmark.”

## 📊 Part 2: Diagram - Async vs Sync

| 🔄 Feature             | Synchronous Code         | Asynchronous Code              |
| ---------------------- | ------------------------ | ------------------------------ |
| Thread usage           | Blocks the thread        | Frees thread while waiting     |
| Scalability            | Poor (1 task = 1 thread) | High (many tasks, few threads) |
| CPU usage              | Idle during I/O wait     | CPU free for other work        |
| Example (`HttpClient`) | Blocks until done        | Returns Task, resumes later    |

## 🔧 Part 3: `ConfigureAwait(false)` — What and Why?

### ✅ What does `ConfigureAwait(false)` do?

It tells the await to **not try to resume** on the **original context** (like UI thread or ASP.NET request context).

```csharp
await SomeAsyncMethod().ConfigureAwait(false);
```

* ✅ Good in **library code**, **background tasks**
* ❌ Not used in **UI apps** (WinForms, WPF), where you must resume on UI thread

---

### ⚠️ Why it's important:

Without `ConfigureAwait(false)`, you may cause:

| Problem           | When                                                   |
| ----------------- | ------------------------------------------------------ |
| Deadlocks         | In ASP.NET / UI apps using `.Result` or `.Wait()`      |
| Thread starvation | If too many async calls try to resume on a busy thread |

✅ Using `ConfigureAwait(false)` helps **free up threads** and **avoid deadlocks**

## 🧠 Thread Pool vs Async

### 🔹 When do `async` methods use the thread pool?

| Case                                    | Thread Pool Used?        |
| --------------------------------------- | ------------------------ |
| I/O-bound task (`HttpClient`, file, DB) | ❌ No                     |
| `await Task.Delay(...)`                 | ❌ No (timer-based)       |
| CPU-bound work (`Task.Run(...)`)        | ✅ Yes — uses thread pool |
| Background processing                   | ✅ Often uses thread pool |

The goal of task asynchronous programming is to enable code that reads like a sequence of statements, but executes in a more complicated order. Execution is based on external resource allocation and when tasks complete.

Cooking breakfast is a good example of asynchronous work that isn't parallel. One person (or thread) can handle all the tasks.

For a parallel algorithm, you need multiple people who cook (or multiple threads). One person cooks the eggs, another cooks the hash browns, and so on.

The await keyword provides a nonblocking way to start a task, then continue execution when the task completes.

The thread doesn't block while the eggs or hash browns are cooking, but the code also doesn't start other tasks until the current work completes. You still put the bread in the toaster and stare at the toaster until the bread pops up, but you can now respond to interruptions.
