# Q1-6: What are the pros and cons of server-side rendering (SSR) in Next.js?

- Server-Side Rendering means the page is rendered on the server at request time, and the HTML is sent to the browser.
- In Next.js, you enable SSR using `getServerSideProps()`.

- Pros:

| Benefit               | Explanation                                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Better SEO            | Search engines can crawl fully rendered HTML, which improves indexing. Useful for blogs, product pages, etc.              |
| Faster initial load   | Users get pre-rendered HTML immediately (TTFB is fast). Good for slower devices.                                          |
| Always fresh data     | Content is rendered on each request—no stale pages. Great for dynamic content like dashboards, prices, or real-time data. |
| No hydration mismatch | Since the server sends a fully rendered page, hydration is more predictable.                                              |

- Cons:

| Drawback                         | Explanation                                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Slower performance under load    | Because every request must be rendered on the server, it can become slow or expensive under heavy traffic.      |
| Higher hosting cost              | Requires Node.js backend to stay online; can’t use static/CDN-only hosting.                                     |
| Complex caching needed           | You often need to implement manual caching (e.g. with Redis or CDN) to avoid performance bottlenecks.           |
| Longer Time to Interactive (TTI) | Even though the HTML loads fast, it still needs JavaScript to become interactive—slower than SSG in some cases. |

- Use SSR when:

    - Data changes often and must always be up to date.
    - SEO is important.
    - You need to use cookies or headers to personalize content per request (e.g., user dashboards, auth pages).

- Avoid SSR when:

    - The data is static or changes rarely → prefer SSG or ISR.
    - You want to serve pages from CDN with high performance and low cost.
    - Your app doesn’t need to be SEO-optimized (e.g., internal admin panels).
